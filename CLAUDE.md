## Project overview

Registro is a personal-management mobile app built with Expo/React Native. All data lives in local SQLite and the app works 100% offline. Since Phase 3 it signs in with Google through Supabase Auth. Since Phase 4 it syncs local data with Supabase Postgres (push of the outbox + pull with a cursor); since Phase 5 (1.3.0) sync is ON in both variants, each against its own project: production → **Poguis**, dev → **Registro Dev**. **Status: Fases 0–6 cerradas (cierre `f97227f`); Fase 7: 7.1 (fixtures saneados) y 7.2 (análisis de entretenimiento, `d55b5e1`) cerradas sin APK, 7.3 (motor puro, `241c26e`), 7.4a (historial como conteo, ciclo y correcciones, `90ea3b5` + corrección `47f358c`) y 7.4b (historial de ritmo, fecha de inicio fija, R10–R12; migraciones Supabase 5 y local 6, `20ad1cb`) cerradas con APK; dirección visual (tema A, Plus Jakarta Sans, hojas propias, nombres largos; `c8eb200`) 7.5 (vínculo Pendiente↔Series/Lectura y subtipo de lectura; migraciones Supabase 6 y local 7; `c2c42c2` + corrección `1f1eec8`) y 7.5b1 (etiquetas por sección, `backlog_tags` y `backlog.tags`; migraciones Supabase 7 y local 8; `1d8d756` + correcciones `a0a4cfc` y `78d8755`: título completo en Pendiente, HojaConTeclado/HojasHost, alturaHoja) cerradas con APK; rediseño de entretenimiento en curso (7.5b2 en dos subfases: **7.5b2a Pendiente compacto en curso** — `app.json` 1.4.5 / vc 19, sin APK todavía; después 7.5b2b, 7.6, 7.7, 7.7b…; el rediseño completo de las pantallas va después de la 7.11), see `claude/DISENO-ENTRETENIMIENTO.md`; app 1.4.4 / vc 18** (local `user_version` 8; 7 migraciones de Supabase; 16 tablas sincronizadas); rest of the Phase 7 backlog: `claude/TRASPASO-FASE7.md`. It covers:
- Finances / balance tracking, debts & loans
- Series/Anime/Reading tracking with quota-based backlog calculations
- Backlog (pending items)
- Work (`Trabajo`), Services (`Servicios`), Cards (`Cards`)

The UI and comments are in Spanish; keep new user-facing strings and comments consistent with that.

### Building an APK

Cloud build (uses EAS credits):
```bash
npm install -g eas-cli
set EAS_NO_VCS=1 && eas build --profile preview --platform android
```

Local build (no EAS credits), one command per variant (`scripts/build-apk.mjs`):
```bash
npm run build:release   # com.poguis.Registro, signed with the EAS keystore → .local-data/apk/registro-release-<version>-vc<code>-<commit>[-mod-<stamp>].apk
npm run build:dev       # com.poguis.Registro.dev, release-mode (embedded JS) signed with debug.keystore (fac61745…) → .local-data/apk/registro-dev-<version>-vc<code>-<commit>[-mod-<stamp>].apk
```
Each one: stops the Gradle daemon (on Windows it locks `android/app/build` and `--clean` fails with EBUSY), runs `npx expo prebuild -p android --clean` with the variant, ensures `sdk.dir`, runs `gradlew assembleRelease` with JDK 17, copies the APK to `.local-data/apk/`, prints applicationId, versionName/versionCode (aapt2) and the certificate SHA-256 (apksigner), and runs `verificar-secretos --apk`. **The production build fails if the fingerprint is not `3132ded2…3e52`: do not install it.** `-mod-<stamp>` means the working tree had uncommitted changes. Needs `.env` (see `.env.example`): `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (production project) and `EXPO_PUBLIC_SUPABASE_DEV_URL` / `EXPO_PUBLIC_SUPABASE_DEV_PUBLISHABLE_KEY` (Registro Dev); publishable keys only, never a secret/service_role key. Step-by-step guide: `.agent/workflows/build-apk-windows.md`. `android/` is generated and git-ignored: never edit it by hand (a copy of the pre-Phase-3 folder is in `.local-data/android-respaldo-fase2/`).

Variants (`app.config.js`, `APP_VARIANT`; `app.json` keeps the static values): production `com.poguis.Registro` / "Registro" / scheme `poguis-registro`; development (`APP_VARIANT=development`) `com.poguis.Registro.dev` / "Registro Dev" / scheme `poguis-registro-dev`. They install side by side, each with its own DB. `app.config.js` puts ONLY the variant's project in `extra.supabase = { url, key }` (the app never reads `process.env`) and `extra.syncEnabled` (`true` in both since Phase 5; emergency switch-off = `false` + a new `versionCode`, since versions cannot go down), so a release APK never contains Registro Dev and vice versa. Current version: `versionName` 1.4.5, `versionCode` 19 in `app.json` since 7.5b2a (installed on the devices: 1.4.4 / 18 until its APK; bump both for every APK that will be installed). Never uninstall: schema changes go as versioned migrations; install on top (`install -r`) with the same keystore, after checking the fingerprint with `apksigner verify --print-certs` (`D:\Users\Carlos\AppData\Local\Android\Sdk\build-tools\36.0.0\apksigner.bat`, the version `scripts/build-apk.mjs` uses; 34.0.0 does not exist on this PC).

## Supabase (`supabase/`)

- `supabase/migrations/<YYYYMMDDHHMMSS>_<nombre>.sql`: the Postgres schema (Phase 2). ## Architecture

There is no router/navigation library (`@react-navigation/*`, `react-native-screens` and `react-native-gesture-handler` were removed in Phase 6.4 as unused) — navigation is a hand-rolled state machine. `react-native-safe-area-context` is used (`SafeAreaProvider` in `App.js`, `SafeAreaView` in the screens).

- **Entry point**: `index.js` → `App.js`.
- **Navigation**: `App.js` holds `currentView` (a string like `HOME`, `DINERO`, `SERIES_DETAIL`, ...) plus a `navigationHistory` stack in local state. A big `switch` in the render body maps `currentView` to a screen component. `handleNavigate(view)` pushes onto history; `handleBack()` (also wired to the Android hardware back button) pops it, or exits the app / shows a confirm dialog when the history is empty at `HOME`. When adding a new screen: add a `case` in the `App.js` switch, plus calls to `onNavigate('NEW_VIEW')` from wherever it should be reachable, and pass `onBack` through.
- **Auth** (Phase 3, `src/auth/`; the UI never imports supabase-js): Google login with Supabase OAuth + PKCE. `googleAuth.ts`: `signInWithOAuth({ provider: 'google', options: { redirectTo, skipBrowserRedirect: true } })` → `WebBrowser.openAuthSessionAsync` (Chrome Custom Tabs) → `exchangeCodeForSession(code)`; the redirect is EXACTLY `<scheme>://auth/callback` (`redirect.ts`; it must match Supabase's Redirect URLs or Supabase falls back to the Site URL). Hermes has no `crypto`: `cryptoShim.ts` provides `getRandomValues` + SHA-256 via `expo-crypto` so auth-js uses `S256` (otherwise Math.random + `plain`). Client (`supabase.ts`): Project URL + publishable key from `Constants.expoConfig.extra.supabase` (the variant's project, see Variants), `flowType: 'pkce'`, `detectSessionInUrl: false`, `autoRefreshToken` started/stopped with `AppState`; if the env vars are missing the login shows an error but the app still opens local data. Session storage: `LargeSecureStore` (`secureStorage.ts`, Supabase's official Expo pattern): a new AES-256 key per write in `expo-secure-store` (excluded from Android Auto Backup) and the session AES-CTR-encrypted in AsyncStorage; leftover PKCE verifiers are deleted after every attempt. `accountFlow.ts`: the startup identity comes from the local `users` table, never from the network, so with local data the app ALWAYS opens (offline, expired token or signed out); only an install without data shows "Continuar con Google". Deferred default categories (Phase 6.6): with sync ON, `createLinkedUser` on a DB without users does not seed; it writes `sync_meta.default_categories_pending` = uid, and `syncOnce` calls `seedPendingDefaultCategories` (users.ts, via `mutate`) right after a COMPLETE pull of `finance_categories`. It creates only the default names with no row at all (live or deleted, so a deleted default never revives), enqueues them, clears the marker (NULL) and sets `default_categories_seeded_at` in the same transaction; anything seeded is pushed in the same cycle. With sync OFF it seeds immediately as before; existing installs never get the marker. Unlinked data shows a non-blocking "Vincula tu cuenta de Google". Linking (`src/data/db/linkAccount.ts`) is a one-time operation (physical copy + exclusive transaction) that rewrites `users.id` and `user_id` in the 15 tables to `auth.uid()`, removes `@user_session` and enqueues nothing, after a confirmation screen showing the Google email (`LinkAccountScreen`). One Google account per device: another account, or several local accounts, is blocked without changes. "Cerrar sesión" signs out of Google only (data kept, app stays open), also offline (Phase 6.5, `signOutLocal.ts`): if `signOut({ scope: 'local' })` fails (expired token, no network), the session is removed from `LargeSecureStore` with the key taken from the client (`auth.storageKey`) and `signOut` runs again, which then does not need the network (`_removeSession`: `SIGNED_OUT`, no resurrection by an in-flight refresh). The button shows with a session or with `sessionOffline`. Rule: the app never signs out on its own; the only exception is auth-js discarding the session when the server definitively rejects the refresh token (revoked session or deleted user). `RlsTestScreen` / `rlsProbe.ts` exist only in the dev variant. Testing notes: the first time, Chrome may show its welcome screen; if the login ends at `localhost`, close the tab and retry. While the Google consent screen is in "Testing", Google shows "Google no verificó esta app" → Continuar.
- **Screens**: `src/screens/*.js` — one file per screen, receiving `user`, `onBack`, and sometimes `onNavigate`/`category` as props from `App.js`. Detail flows (e.g. Series → SeriesDetail → ChapterRegistry, or Reading → ReadingDetail → ReadingRegistry) pass a `selectedCategory` object down through `App.js` state rather than through navigation params.
- **Sync** (Phase 4, `src/sync/`, TypeScript; the UI only uses `useSync` / `useSyncRefresh` and never imports the engine or supabase-js):
  - `engine.ts`: `syncOnce` = checks (sync enabled, linked account, `users.id` = session uid, valid session; otherwise `skipped` with a reason) → **push** of the outbox (snapshot of ready entries, grouped by row, current row state mapped with `toRemote`, upsert by `id` in batches of 100 in parent → child order; confirmed outbox ids deleted) → **pull** of the 15 tables (pages of 500 ordered by `server_updated_at, id` with the keyset `or(...)` plus a redundant `server_updated_at >= cursor` range since 1.3.2 (`applyPullFilter`), cursor per table in `sync_state` stored exactly as returned, 60 s overlap window; rows with a pending/blocked outbox entry or identical content are skipped) → `sync_meta`. Errors: network/timeout/408/429/5xx → backoff `min(30 s·2^attempts, 1 h)` tagged `red · `; auth (401/JWT) → stop without blaming entries; 23505 → natural-key merge (`finance_categories(user_id, name)`, `seasons(series_id, season_number)`: the local row adopts the server id); 23503 → enqueue the parent; anything else → `blocked_at`/`block_reason` (shown in the UI, "Reintentar" = `unblockAll`), never deleted. Last write to reach the server wins. Phase 7.5: `backlog` comes before `series` in `TABLES` (`series.backlog_id`); a 23503 never takes a NULL FK as the missing parent; the pull applies and compares ONLY the columns the remote row carries (a server without a new column never NULLs the local value); "Reintentar" (`unblockAll`) also frees entries waiting for a blocked parent (`last_error` = the exported constant `PARENT_BLOCKED`), never network/session ones; after the complete pull of `series`, `reconcileLinkedTitles` runs via `mutateFromSync` and its writes are pushed in the same cycle (the generalized 6.6 `push2`). Phase 7.5b1: 16 synced tables; `backlog_tags` goes LAST in `TABLES` (no domain FK; against a server without the table its pull fails after the others: the cycle ends `offline`, nothing is lost), with `NATURAL_KEYS.backlog_tags = (user_id, section, name_key)` (nobody references it by id) and the mapping kind `tags` (canonical form of `backlog.tags`, also on pull and in `sameAsLocal`). `syncWithWatchdog`: a cycle over 2 min is failed and cancelled cooperatively. `supabaseTransport.ts` implements `transport.ts` (fetch with a per-request timeout); tests use `scripts/lib/pglite-transport.mjs`.
  - `runner.ts`: single-flight (one sync at a time; requests during a run merge into ONE extra run). Reasons `reconexion` and `boton` first reset the backoff of network-tagged entries (`resetNetworkBackoff`). After each cycle, if the sync wrote local data (pull applied rows or a merged id: `takeLocalDataChanged`), it calls `onDataChanged`.
  - First upload (Phase 5): `ensureInitialUpload` (engine) enqueues ONCE per device every row (live and tombstones) of the 15 tables, in one `localTx` with the marker `initial_upload_done_at` / `initial_upload_uid` / `initial_upload_summary` (counts only) in `sync_meta`; needs sync enabled + a linked account, no network or session; idempotent. The runner runs it as `prepare` before EVERY cycle (one read once the marker exists), serialized with app writes (`localTx` → `enqueue`), so it is done before the first cycle whatever the trigger, also offline and right after linking (App.js remounts `startSyncTriggers` when `user` changes). It never fires the outbox listener.
  - Offline ≠ no session (`src/auth/sessionState.ts`): with a stored but expired session and no network, auth-js 2.118 `getSession()` returns `session: null` + `AuthRetryableFetchError`; `readSessionState` reports `offline: true` only then (no stored session → `offline: false`). The transport returns `{ offline: true }` and `syncOnce` ends `offline` (outbox untouched, "Sin conexión — N"); Home does not ask to sign in (`useAuth().sessionOffline`). No lock in RN: auto-refresh and the cycle share one in-flight refresh. After a failed refresh auth-js returns the same failure for 60 s (`REFRESH_FAILURE_COOLDOWN_MS`).
  - Triggers, registered only in `controller.ts` `startSyncTriggers` (App.js; no-op when sync is disabled): app open, AppState → `active`, NetInfo `isConnected` false → true, the "Sincronizar ahora" button, and `autoSync.ts`: after every local transaction that enqueued outbox entries (`setOutboxCommitListener` in `connection.ts`; the engine writes the outbox outside `tx()`, so it never triggers itself) a cycle with a 3 s debounce, only when connected; and a periodic cycle every 2 min only in the foreground and connected, scheduled after the previous one ends and skipped while a sync runs; and `TOKEN_REFRESHED` (only that auth event, `subscribeSessionRestored`) → `requestSync('sesion')` only if the last cycle ended `offline` or skipped with `no-session` / `session-expired` (`shouldSyncOnSessionRestored`; covers the 60 s cooldown). Reasons `reconexion`, `boton` and `sesion` reset network backoff. No background tasks. Timings in `config.ts` (`changeDebounceMs`, `periodicMs`).
  - UI: `SyncStatus.js` on Home (only when `syncEnabled`) shows synced / syncing / offline with N pending / sign in / N errors with detail and "Reintentar"; "pending" = DISTINCT rows with unsent changes (not raw outbox entries). The text comes from the pure function `describeSyncStatus` (`src/sync/syncStatusText.ts`, Phase 6.5): offline per NetInfo → "Sin conexión" / "Sin conexión — 1 cambio pendiente" / "— N cambios pendientes" (first rule, so offline never asks to sign in); a cycle running or pending rows → "Sincronizando…"; otherwise "Sincronizado hace X". `controller.ts` exposes `getConnectivity()` from its single NetInfo listener and notifies the UI on connectivity changes and after each commit that enqueues (local re-read only, no cycle). Screens that show data call `useSyncRefresh(reload)`: when a cycle changed local data they re-read the DB without resetting forms, filters or scroll (Registros reloads silently, without the loading spinner). New data screens must do the same.
  - Migration 4 (`src/data/db/migration4.ts`; current `user_version` is 8 since Phase 7.5b1): `outbox.blocked_at` / `block_reason` + index, `sync_state`, `sync_meta`; no data changes. `sync_meta` keys: `last_attempt_at`, `last_success_at`, `last_error`, `initial_upload_done_at` / `initial_upload_uid` / `initial_upload_summary` (Phase 5), `default_categories_pending` / `default_categories_seeded_at` (Phase 6.6), `backup_cleanup_first_at` / `backup_cleanup_last_at` / `backup_cleanup_last_summary` (Phase 6.7, counts only).
